# Передача сайта клиенту: какой сервер взять и как переехать

Коротко: сайт — статика плюс один PHP-скрипт приёма заявок, поэтому
сервер нужен самый маленький. Весь сервер собирается из репозитория
одной командой, так что переезд — это «поднять новый, проверить его
мимо DNS, переключить записи». Руками переносить нужно ровно два
файла: почтовые настройки и накопленные заявки.

---

## 1. Какой сервер брать

Что сайту нужно на самом деле: nginx, PHP-FPM и 300 МБ файлов.
Посетителей он держит тысячами — отдаются готовые страницы.

| | Минимум | Рекомендую |
|---|---|---|
| Ядра | 1 | 2 |
| Память | 1 ГБ | 2 ГБ |
| Диск | 10 ГБ | 20–30 ГБ NVMe |
| Система | Ubuntu 24.04 LTS | Ubuntu 24.04 LTS |
| Площадка | — | Россия (Москва или Санкт-Петербург) |

Два ГБ памяти — не ради нагрузки, а чтобы обновления системы и выпуск
сертификата не упирались в нехватку памяти на гигабайтной машине.

**Почему площадка в России.** На сайте форма с именем и телефоном —
это персональные данные, и 152-ФЗ требует, чтобы они собирались на
серверах в России. Заодно это быстрее для посетителей из Твери и
понятнее Яндексу.

**Где брать.** Любой из российских: Timeweb Cloud, Selectel, Beget,
Reg.ru, Aeza. Разница для нашего случая невелика, поэтому выбирайте
по удобству клиента:

- **Reg.ru** — если домен каркаскомфорт.рф остаётся там же: один
  аккаунт, один счёт, одна панель. Меньше всего шансов, что клиент
  забудет что-то продлить.
- **Timeweb Cloud или Selectel** — приятнее панель, бэкапы в два
  клика, поддержка отвечает быстрее.

Ориентир по деньгам — порядка 500–1000 ₽ в месяц за такую машину;
точную цену смотрите в тарифах на момент покупки, они меняются.
Обязательно включите **ежедневные резервные копии** (обычно +20–30 %
к тарифу) и **автоплатёж**: самая частая причина, по которой сайт
внезапно пропадает, — закончились деньги на балансе, а не поломка.

**Стоит ли вообще VPS.** Сайту хватило бы обычного хостинга за
200–300 ₽: там сертификат, панель и бэкапы уже настроены, а выгрузка
по FTPS у нас готова (workflow «Deploy site»). VPS имеет смысл, если
клиент хочет полный контроль, свою почту на домене или собирается
держать на этой машине что-то ещё. Если у клиента нет человека,
который умеет в консоль, — обычный хостинг спокойнее.

## 2. Что передаётся кроме файлов сайта

| Что | Где сейчас | Как передать |
|---|---|---|
| Домен каркаскомфорт.рф | аккаунт регистратора | «Передача домена другому пользователю» в панели регистратора |
| Сервер | VPS | клиент заводит свой и оплачивает со своей карты |
| Исходники сайта | GitHub `dkaratsapov-web/karkas_comfort` | Settings → Transfer ownership, нас оставить коллаборатором, пока ведём сайт |
| Почта для заявок | `api/config.php` на сервере | клиент вписывает свой адрес сам |
| Telegram-бот для заявок | токен в `api/config.php` | клиент создаёт своего бота у @BotFather |
| Накопленные заявки | `api/leads.csv` на сервере | скопировать при переезде (см. шаг 3) |
| Яндекс.Вебмастер, Метрика, Search Console | панели | добавить клиента владельцем, затем снять себя |

Доступы к серверу и токены **не пересылаются перепиской**: пароль
клиент задаёт у провайдера сам, ключ выгрузки генерируется на сервере
и попадает только в секреты GitHub.

## 3. Переезд без простоя

Порядок важен: сначала новый сервер полностью готов и проверен, и
только потом переключается домен. Старый всё это время работает.

**За сутки до переезда.** В DNS домена уменьшить TTL у записей `@` и
`www` до 300 секунд. Тогда переключение подхватится за пять минут,
а не за сутки.

**Шаг 1. Сервер.** Клиент создаёт VPS с Ubuntu 24.04 и даёт root-доступ
на время переноса (после переезда пароль меняется).

**Шаг 2. Настройка одной командой** (от root на новом сервере):

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/dkaratsapov-web/karkas_comfort/claude/karkas-comfort-redesign-0zy3xi/server/bootstrap.sh) \
     --domain xn--80aa2abbmnbmggrx.xn--p1ai \
     --email  почта-клиента@example.ru
```

Скрипт ставит nginx, PHP-FPM, certbot и брандмауэр, заводит
пользователя `deploy`, раскладывает каталоги, создаёт ключ для выгрузки
и печатает его в конце. Сертификат он выпустить пока не сможет — домен
ещё смотрит на старый сервер, это нормально.

**Шаг 3. Перенести со старого сервера то, чего нет в репозитории** —
почту и токены (`api/config.php`), накопленные заявки (`api/leads.csv`),
сертификат и ключ выгрузки. Одной командой на новом сервере, от root:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/dkaratsapov-web/karkas_comfort/claude/karkas-comfort-redesign-0zy3xi/server/migrate-from.sh) \
     --from СТАРЫЙ_IP
```

Пароль старого сервера спросят один раз. Скрипт только читает со старого
сервера, ничего там не меняя, и его можно запускать повторно: заявки он
не перезаписывает, а сливает, поэтому через неделю после переезда тем же
вызовом забирается хвост заявок, упавших на старый сервер.

Отдельно о сертификате: он переносится целиком, поэтому https заработает
в ту же секунду, что и переключение DNS, без предупреждения браузера.
И о ключе: открытый ключ выгрузки переезжает со старого сервера, значит
в секретах GitHub достаточно поменять один `VPS_HOST`.

**Шаг 4. Выгрузить сайт.** В GitHub (Settings → Secrets and variables →
Actions) поменять `VPS_HOST` на адрес нового сервера. Остальные три
секрета остаются прежними, если шаг 3 перенёс ключ; если нет — задать
заново: `VPS_USER` (`deploy`), `VPS_PATH`
(`/var/www/xn--80aa2abbmnbmggrx.xn--p1ai/public`), `VPS_SSH_KEY` — ключ,
который напечатал bootstrap. Затем Actions → «Deploy to VPS» → Run
workflow. В конце лога будет список адресов с кодами ответа.

**Шаг 5. Проверить новый сервер до переключения домена.** Сайт
проверяется по IP, но с подстановкой имени домена — так же, как его
увидят посетители:

```bash
curl -sk -o /dev/null -w '%{http_code}\n' --resolve xn--80aa2abbmnbmggrx.xn--p1ai:443:НОВЫЙ_IP https://xn--80aa2abbmnbmggrx.xn--p1ai/
```

Должно быть `200`. То же для `/proekty/`, `/obekty/`, `/kontakty/`.
Если проверяете глазами — пропишите пару «IP домен» в файл hosts на
своём компьютере.

**Шаг 6. Переключить DNS.** В панели регистратора заменить A-записи
`@` и `www` на новый IP. Пять–тридцать минут — и домен на новом сервере.

**Шаг 7. Сразу после переключения.**

```bash
certbot renew --dry-run     # продление сертификата работает
```

И руками: отправить тестовую заявку с сайта, убедиться, что письмо
пришло и Telegram сработал.

**Шаг 8. Старый сервер.** Не выключать сразу — держать неделю. Через
неделю забрать хвост заявок (`api/leads.csv`), убедиться, что в нём нет
ничего нового, и только тогда удалять машину.

## 4. Смена доступов после переезда

- На новом сервере завести **новый** ключ выгрузки, старый из
  `~deploy/.ssh/authorized_keys` убрать.
- Пароль root и учётную запись у провайдера клиент меняет сам.
- Репозиторий перевести в аккаунт клиента, секреты в нём задать заново
  (при переносе репозитория секреты не переезжают).
- Токен Telegram и доступы CRM — только в `api/config.php` на сервере;
  в репозитории их нет и быть не должно.

---

## 5. Что остаётся клиенту

- Оплата сервера и домена (автоплатёж).
- Сертификат продлевается сам, `certbot.timer` уже включён.
- Резервные копии — на стороне провайдера, проверить раз в месяц, что
  они создаются.
- Правки сайта: коммит в репозиторий → сборка и выгрузка идут сами.

Если меняется домен (а не только сервер), поменять его нужно в четырёх
местах: `src/data/site.json`, шаблон `server/nginx-site.conf.template`,
проверки в `.github/workflows/deploy-vps.yml` и команда запуска
`server/bootstrap.sh`.
