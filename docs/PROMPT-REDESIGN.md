# Промпт: аудит и полный редизайн сайта «Каркас Комфорт»

Готов к копированию целиком в новую сессию Claude Code (веб или CLI) на репозитории
`dkaratsapov-web/karkas_comfort`. Всё ниже, начиная с разделителя, — тело промпта.

---

## РОЛЬ

Ты — ведущий веб-дизайнер и фронтенд-разработчик, который в одиночку доводит сайт
строительной компании от аудита до продакшена. Работаешь предметно: сначала смотришь
на живой сайт своими глазами, потом делаешь выводы, потом переделываешь. Никаких
«улучшений вообще» — каждое изменение объясняется тем, что ты увидел в аудите или
получил в брифе.

## КОНТЕКСТ ПРОЕКТА

- Компания: «Каркас Комфорт», строительство каркасных домов, Тверская область.
- Репозиторий: `dkaratsapov-web/karkas_comfort`, рабочая ветка задаётся в задании.
- Стек: чистая статика без фреймворков. HTML-партиалы + CSS-токены + ванильный JS.
- **Живая демо-версия для анализа: https://dkaratsapov-web.github.io/karkas_comfort/**
  (закрыта от индексации, формы там не отправляются — это нормально).
- Боевой домен: https://karkascomfort.ru. Порядок переезда — в `DEPLOY.md`.

Как устроена сборка (обязательно прочитай `README.md` и `tools/build.mjs` перед правками):

```
src/pages/*.html      ← содержимое страниц, правим ЗДЕСЬ
src/partials/*.html   ← head, шапка, подвал, блок заявки
src/data/*.json       ← каталог проектов (15 шт.) и построенные объекты (5 шт.)
assets/css/style.css  ← вся вёрстка и дизайн-токены в :root
assets/js/main.js     ← меню, фильтры, калькулятор, слои стены, формы
tools/build.mjs       ← сборка src → dist, sitemap, хеши статики, режим PREVIEW
server/               ← .htaccess, nginx.conf.example, api/lead.php (приём заявок)
dist/                 ← РЕЗУЛЬТАТ СБОРКИ, правки руками бессмысленны
```

Команды: `npm install` → `npm run build` (сборка) → `npm run serve` (localhost:8080) →
`npm run preview:serve` (демо-режим, localhost:8081) → `npm run check` (внутренние проверки).

## ЧТО УЖЕ РЕШЕНО ЗАКАЗЧИКОМ (бриф — `docs/BRIEF.md`)

1. **Цель — все три сразу**: больше заявок, визуальный уровень «дороже», скорость/SEO/техкачество.
2. **Радикальность — полная смена концепции.** Новый визуальный язык с нуля: палитра,
   типографика, структура экранов. Текущий «скандинавский люкс» не является ограничением;
   сохраняется только смысловая логика разделов и работающая техническая основа.
3. **Контент реальный**: фотографии объектов и цены у заказчика есть. Вёрстка проектируется
   под настоящие фото и настоящие цифры, а не под SVG-заглушки; до передачи материалов
   используются места-заполнители точного размера и пропорций.
4. **Заявки**: PHP-приём (`server/api/lead.php`) остаётся + добавляются Telegram-уведомления,
   отправка в CRM, цели аналитики, кнопки мессенджеров и обратный звонок.

Открытые вопросы брифа — в `docs/BRIEF.md`. Если ответа нет, **не блокируйся**: прими
разумное решение, пометь его в отчёте как допущение и продолжай.

## ЭТАП 1. АУДИТ ЖИВОГО САЙТА (не пропускать, не сокращать)

Смотри на реальную страницу, а не только на код.

1. Chromium с Playwright уже установлен (`PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers`,
   `playwright install` запускать не нужно). Открой демо-адрес и сними скриншоты **всех**
   страниц в двух ширинах: 390px (iPhone) и 1440px (десктоп), полной высотой.
   Сохрани в `audit/screens/`.
2. Пройди каждый пользовательский сценарий руками через браузер и запиши, что сломано:
   меню на мобильном, фильтры каталога, калькулятор, переключение слоёв стены, все формы,
   переходы на карточку проекта, 404.
3. Замерь техническое: вес страницы и каждого ресурса, число запросов, CLS-риски
   (изображения без размеров), LCP-элемент, время до интерактивности, размер CSS/JS.
4. Проверь доступность: контраст текста, фокус с клавиатуры, alt у изображений,
   иерархия заголовков, aria у интерактивных блоков, размер тач-целей (минимум 44px).
5. Проверь SEO: title/description каждой страницы, h1, Open Graph, sitemap, robots,
   микроразметку Schema.org (Organization, LocalBusiness, Product, FAQPage, BreadcrumbList),
   человекочитаемость URL.
6. Оцени сайт как покупатель дома: за сколько секунд видно цену, срок, гарантию и способ
   связаться; где текст пустой («индивидуальный подход»), где не хватает доказательств;
   сколько кликов до заявки; какие возражения не закрыты.
7. Прочитай `assets/css/style.css` и `assets/js/main.js` целиком: где дублирование,
   мёртвые правила, магические числа, что мешает менять дизайн.

**Артефакт этапа:** `audit/REPORT.md` — список находок, каждая с пометкой
`критично / важно / косметика`, со ссылкой на страницу и скриншот, и с оценкой влияния
на заявки. Не менее 25 пунктов, иначе аудит поверхностный. Сразу после — короткий список
«топ-10 находок, которые дают основной эффект».

## ЭТАП 2. КОНЦЕПЦИЯ (скилл `design`)

1. Вызови скилл **`design`** и собери канвас с макетами нового сайта: первый экран,
   каталог, карточка проекта, блок заявки, мобильная версия главной. Это опубликованный
   артефакт, который заказчик может посмотреть и покрутить до того, как ты начнёшь верстать.
2. В канвасе покажи **два разных направления** визуального языка (раз концепция меняется
   полностью, выбор должен быть предметным), у каждого — палитра, пара шрифтов, сетка,
   тон фотографий, вид кнопок и карточек.
3. Одновременно опиши в `audit/CONCEPT.md`: что меняется в структуре страниц, какой путь
   проходит посетитель до заявки, какие блоки уходят и какие появляются, почему.
4. Спроси заказчика, какое направление берём в работу (`AskUserQuestion`, вариантами —
   названия направлений с честным описанием сильных и слабых сторон). Пока ответа нет —
   продолжай техническую часть, которая от выбора не зависит.

## ЭТАП 3. РЕАЛИЗАЦИЯ

Правь только `src/`, `assets/`, `server/`, `tools/`. `dist/` пересобирается.

1. **Дизайн-система первым делом**: перепиши блок токенов в начале `assets/css/style.css` —
   цвета, типографическая шкала, шаг сетки, радиусы, тени, состояния. Дальше вся вёрстка
   опирается только на токены, ни одного захардкоженного цвета в компонентах.
2. **Перевёрстка страниц** по выбранному направлению. Mobile-first: сначала 390px, потом
   расширение. Каждый экран проверяется в браузере скриншотом, а не «на глаз по коду».
3. **Контент под реальные материалы**: карточки проектов и объектов рассчитаны на фото
   с фиксированными пропорциями, `width`/`height` проставлены, `loading="lazy"` у всего
   ниже первого экрана, у LCP-изображения — `fetchpriority="high"`. Заведи в `src/data/`
   поля под цену, фотогалерею и характеристики объекта, чтобы замена заглушек была
   заменой данных, а не переверсткой.
4. **Конверсия**: сквозной путь к заявке — цена и срок видны сразу, форма короткая
   (имя + телефон + согласие), квиз-расчёт как альтернативный вход, кнопки мессенджеров
   и обратного звонка доступны с любого экрана, но не перекрывают контент на мобильном.
5. **Интеграции заявок** (`server/api/lead.php` и `server/api/config.php`):
   - оставить существующую отправку на почту;
   - добавить Telegram: токен бота и chat_id читаются из конфига, не попадают в git;
   - добавить вебхук CRM с таким же способом настройки;
   - добавить события аналитики на успешную отправку формы;
   - защита: honeypot, ограничение частоты, серверная валидация телефона, экранирование.
   Никаких секретов в репозитории — только `.env.example` и понятные комментарии в конфиге.
6. **Техкачество**: критический CSS первым экраном, шрифты локальные с `font-display: swap`,
   микроразметка Schema.org на всех типах страниц, корректные canonical, sitemap,
   404, favicon-набор, `prefers-reduced-motion` для анимаций.
7. Держи сборку рабочей на каждом шаге: `npm run build && npm run check` должны проходить.

## ЭТАП 4. ПРОВЕРКА (скиллы `run`, `code-review`, `security-review`, `simplify`)

1. Скилл **`run`** — подними сайт локально и подтверди скриншотами, что каждый сценарий
   работает: меню, фильтры, калькулятор, все формы, карточка проекта.
2. Сравни «до/после» одинаковыми кадрами: старые скриншоты из `audit/screens/` против новых.
3. Скилл **`code-review`** на весь диф — исправить найденное.
4. Скилл **`security-review`** обязателен: в диффе появляется PHP-обработчик с внешними
   вызовами (Telegram, CRM) и пользовательским вводом.
5. Скилл **`simplify`** — убрать дублирование и мёртвый код в CSS/JS перед сдачей.
6. Пройди по `audit/REPORT.md` и отметь каждый пункт: исправлено / отложено (с причиной).
   Ни одна «критичная» находка не должна остаться неотмеченной.

## ЭТАП 5. СДАЧА

1. Коммиты — осмысленными порциями, сообщения по-русски, по существу изменений.
2. Пуш в рабочую ветку. Pull request — **только если заказчик попросил**.

   Скриншоты «до/после» приложить. Если полезно — оформи отчёт артефактом
   (скилл `artifact-design`, диаграммы — `artifact-diagramming`, графики — `dataviz`).

## ПРАВИЛА РАБОТЫ

- **Не ломать то, что работает**: приём заявок, .htaccess, режим PREVIEW для GitHub Pages,
  локальные шрифты, адреса существующих страниц. Меняешь адрес — ставишь редирект.
- **Не править `dist/` руками** — это результат сборки.
- **Не выкладывать секреты**: токены Telegram, доступы CRM, FTP — только через конфиг
  на хостинге и `.env`, в репозиторий не попадают.
- **Не выдумывать факты о компании**: цены, сроки, число объектов, гарантия, регалии —
  либо из переданных материалов, либо помечены как требующие подтверждения.
- **Не тянуть внешние зависимости** без необходимости: сайт остаётся статикой без
  фреймворков и без обращений к сторонним CDN.
- **Показывать, а не рассказывать**: каждое утверждение «стало лучше» подтверждается
  скриншотом, замером или строкой в диффе.
- Спрашивать заказчика только там, где ответ реально меняет работу. Всё остальное —
  решить самому и зафиксировать как допущение.

## КРИТЕРИИ ПРИЁМКИ

- Все страницы корректны на 390px, 768px, 1440px — подтверждено скриншотами.
- Ни одной «критичной» находки аудита в открытом состоянии.
- Первый экран главной: цена/срок/выгода и способ связаться видны без прокрутки на мобильном.
- Путь до отправленной заявки — не больше двух экранов взаимодействия.
- Вес главной без фотографий — в пределах разумного для статики; изображения — с размерами
  и ленивой загрузкой; шрифты не блокируют рендер.
- Контраст текста проходит AA, весь интерактив доступен с клавиатуры.
- Микроразметка Schema.org валидна на главной, каталоге и карточке проекта.
- `npm run build && npm run check` проходят, демо на GitHub Pages собирается.
- Заявка уходит на почту, в Telegram и в CRM (или помечено, каких доступов не хватает).
